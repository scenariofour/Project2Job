# Stateful Agent V0 Dogfood

Date: 2026-07-26

Status: real repository evidence execution with host-mediated research and
generation. This is not live-model planner validation and not target-user
validation.

## Inputs and safety boundary

- Project: the existing Etsy 0-1 Auto-Test Lab used in prior dogfood
- JD: a retained TikTok Shop Product Operations Intern posting used only as a
  temporary dogfood fixture; it is not a confirmed target role, canonical
  Project2Job role, or evidence of actual job-search fit

## A. Initial run

The Agent opened five Project evidence files, called two capabilities
(`$p2j-intel` host research and `$p2j-brief` host analysis), regenerated 23
outputs, validated the result, and saved the canonical evidence, claims,
outputs, dependencies, trace, and observed metrics.

The result contains the five visible Project score dimensions, five JD Matches,
two compact intelligence items, seven basis-labeled likely questions, two
interview stories, one Project Verdict, and exactly one route:
`$p2j-upgrade`.

The bounded public pass used eight searches and opened five selected pages.

guidance; one independent Product Operations report page supplied single-report

Boundaries:

- the reported questions are labeled single-report and are not guarantees
- no exact question had enough independent repetition to be labeled repeatedly
  reported
- company research changes emphasis and question priority only; it is not
  Project evidence and did not change the candidate fact set

- the Project-triggered failure question

The trace records Before / After / Why for both and states that the controlled

## D. Upgrade handoff loop

The remaining target-platform design gap routed to `$p2j-upgrade`. The output
prioritized the material gaps, selected one source-grounded TikTok Shop partner
API design and UAT plan, rejected the primary-research runner-up, and produced a
copyable Codex/Claude Code handoff prompt.

The prompt requires repository inspection, architecture preservation, one named
artifact, concrete acceptance checks, real verification, and an exact execution
report. It prohibits invented metrics, users, outcomes, ownership, and test
results. Project2Job did not execute the build.

For loop verification, `tiktok-shop-partner-api-uat-plan.md` and
`p2j-evidence--c_platform.md` were added only to the temporary copy and clearly
labeled simulated proposed artifacts. They are not original candidate evidence
and do not establish direct TikTok Shop experience, a completed integration,
seller or ISV experience, executed UAT, or commercial impact. The next process
opened only the changed evidence record and changed exactly three
planning-related outputs:

- proposed target-platform product design: `GAP` → `TRANSFERABLE`
- the likely technical follow-up
- route: `$p2j-upgrade` → `$p2j-answer`

Twenty outputs were preserved. No actually executed new result was added during
this dogfood. This verifies the mechanism; it is not evidence that a target user
completed or valued the handoff.

## E. Interview path

Codex used the existing `$p2j-answer` contract on the prioritized
Project-triggered failure question, then passed the grounded answer into the
existing `$p2j-mock` contract. The answer stayed in an observed-project frame
because personal ownership is unresolved.

The Mock exposed one precise weakness: the answer states the repair sequence
but leaves the rejected alternative, repair rationale, and ownership boundary
implicit. It supplied narrower replacement wording and one follow-up. The
Project fact set remained seven claims before and after, with zero facts added
or changed.

## Observed stateful versus fresh comparison

The comparison runs the integrated CLI for both paths. The fresh path replays
the same final source-grounded host analysis from scratch; its metrics come
from adapter events and traces, not fixture-assigned numbers.

| Metric | Stateful update | Fresh run |
| --- | ---: | ---: |
| Files opened | 1 | 6 |
| Questions asked | 0 | 0 |
| Capability calls | 1 | 2 |
| Outputs regenerated | 2 | 23 |
| Outputs preserved | 21 | 0 |
| Expected outputs correctly updated | 2 | 2 |
| Unrelated outputs incorrectly changed | 0 | 0 |
| Latency | 1.123 ms | 0.759 ms |
| Token usage | unavailable | unavailable |

The stateful run reduced reads, calls, and regeneration while preserving the
same output correctness in this case. The comparison treats the changed file as
a controlled summary of existing facts, not as new capability evidence. The
local latency difference is too small and environment-dependent to support a
latency advantage claim.
