# Role-Backwards Evidence Framework

## Name

**Role-Backwards Evidence Framework (RBEF)**

RBEF is Career Desk's product method. It is a synthesis, not an academic certification or a universal hiring standard.

## Purpose

Convert a target role into project evidence requirements, then convert supported project evidence into career outputs.

## Six stages

### 1. Role Reality

What does the target role actually do?

Sources:

- current official job descriptions
- product documentation
- role-specific interviews and hiring guidance
- target JD

### 2. Hiring Signal

How could a recruiter or interviewer recognize the capability?

Examples:

- resume evidence
- project artifact
- decision explanation
- measured result
- failure analysis
- cross-functional artifact

### 3. Project Evidence

What in the user's project supports the signal?

Evidence may include:

- README or PRD
- code and configuration
- eval cases and results
- traces
- user research
- design decisions
- failure logs
- metrics
- ownership confirmation

### 4. Evidence Boundary

What can the artifact prove, and what remains unknown?

Allowed statuses:

- Supported
- Partially Supported
- Inferred
- Not Found
- Conflicting
- Needs Confirmation

### 5. Career Translation

Convert only supported evidence into:

- project highlights
- resume bullets
- portfolio content
- interview answer ingredients
- recruiter or networking drafts in later releases

### 6. Evidence Upgrade

Choose one project action that would create the most valuable missing evidence.

## Canonical path

```text
Role Task
→ Hiring Signal
→ Required Evidence
→ User Artifact
→ Supported Claim
→ Career Output
→ Next Evidence Action
```

## Why this method exists

Generic career tools often begin with resume text. RBEF begins with role requirements and project artifacts, then limits career language to what the artifacts support.

## Quality rules

- Role requirements must have source provenance.
- Similar role requirements may be grouped only when their evidence test is the same.
- Project evidence is evaluated for a specific claim.
- Tool usage alone does not prove product judgment.
- A planned feature does not prove execution.
- A self-authored claim is weaker than an independent artifact.
- Missing evidence does not prove the user lacks the capability.
- Career language cannot exceed the evidence boundary.
